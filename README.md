# Plugin Inventory

관심 있는 GitHub AI skill·MCP·plugin의 최근 릴리스와 유지보수 활동을 모아 보는 개인용 공개 웹앱입니다.

- 사이트: https://hyuuShin.github.io/plugin-inventory/
- 관심 도구 등록: https://github.com/hyuuShin/plugin-inventory/issues/new?template=track-tool.yml
- 수집 실행: https://github.com/hyuuShin/plugin-inventory/actions/workflows/update-and-deploy.yml

## 사용하기

1. 사이트의 **관심 도구 추가**에서 GitHub 입력 양식을 엽니다.
2. `hyuuShin` 계정으로 주소·유형·용도 분류·사용법 메모를 제출합니다.
3. 수집과 배포가 끝나면 목록에 반영됩니다. 마지막 수집 시각과 실행 링크로 진행 상태를 확인합니다.

수정은 원래 Issue의 본문 편집, 목록에서 제외는 Issue 닫기, 복원은 다시 열기입니다. 닫아도 공개된 Issue와 Git 이력은 남습니다. 외부인이 만든 Issue는 목록에 반영되지 않으며 자동 댓글을 달지 않습니다.

저장소 주소와 기본 브랜치의 `tree` 폴더·`blob` 파일 주소를 지원합니다. 파일은 해당 파일만 추적하며 다른 브랜치나 고정 SHA는 지원하지 않습니다. 개별 경로의 커밋과 저장소 전체의 릴리스를 구분합니다.

## 자동 갱신과 주간 발견

- 매일09:17 KST 관심 목록·후보 관측, 월요일09:43 KST 주간 발견 발행.
- GitHub 스케줄은 지연되거나 누락될 수 있습니다. 48시간 이상 지난 자료와 9일 이상 지난 주간 자료에는 안내가 표시됩니다.
- **Run workflow**의 `daily`로 자료를 갱신하고, `weekly`로 후보 검색과 주간 발행을 실행할 수 있습니다. `dry_run`은 수집·검증만 하고 커밋·게시하지 않습니다.
- GitHub의 공개 저장소 예약 작업은 저장소 활동이60일 없으면 꺼질 수 있습니다. Actions 화면에서 작업을 다시 켜고 수동 실행하세요.
- 첫 주에는 비교 이력이 부족하므로 새로 찾은 후보만 표시합니다. 약1주일 관측 뒤 실제 별 수 차이를 비교합니다. 별 증가가 양수이고 비교 날짜가6~8일 떨어진 후보만 주간 변화에 소개합니다.
- 검색은 설정한 GitHub 주제와 이름·설명의 한정된 범위를 사용합니다. 전체 GitHub의 공식 Trending이나 검증된 설치 목록이 아닙니다. 후보는 관심 목록에 자동으로 들어가지 않습니다.
- 생성형 AI·자동 번역·유료 API를 사용하지 않습니다. 설명은 GitHub 원문과 직접 작성한 한국어 메모입니다.

## 정보의 의미

릴리스가 없다고 관리 중단으로 판단하지 않습니다. 최근90일 변경 없음, 저장소 보관됨, 경로 없음, 수집 실패를 각각 표시합니다. 실패 시 마지막 성공 자료를 보존하며 미확인 기간을 활동0으로 채우지 않습니다. 설치 여부나 설치 버전은 수집하지 않습니다.

등록 최대100개, 후보 최대200개를 추적합니다. 최근90일의 관측과52주의 주간 자료를 현재 파일에 보관하며 과거 Git 이력은 별도로 남습니다. 수집 한도에 도달하면 일부 집계임을 표시합니다.

## 로컬 실행

Node.js22 이상이 필요합니다. 필수 npm 의존성은 없습니다.

```sh
npm test
npm run build
npm run check
npm run preview
```

로컬 주소는 http://localhost:4173/plugin-inventory/ 입니다. `config/app.json`의 소유자·저장소·basePath를 함께 관리합니다. 브라우저는 배포한 JSON만 읽고 방문할 때마다 GitHub API를 호출하지 않습니다.

수집기를 직접 실행할 때는 해당 공개 자료를 읽을 수 있는 작업용 토큰을 프로세스 환경으로 전달하고 `npm run collect -- --mode daily`를 실행합니다. 토큰을 소스·URL·브라우저 저장소에 넣지 마세요. 로컬 `gh`의 기본 계정은 변경할 필요가 없습니다. 계정을 명시한 관리 도구는 구현 계획의 배포 검증 단계에서 사용합니다.

## 배포와 복구

표준 Ubuntu Actions 실행기와 GitHub Pages만 사용합니다. 공개 저장소의 표준 실행기 무료 범위 및 GitHub의 사용 한도가 적용되며, 별도 서버·DB·유료 API 키는 필요하지 않습니다. Artifact는1일 보관하고 larger runner나 장기 캐시는 사용하지 않습니다.

수집·자료 저장·Pages 배포는 하나의 실행에서 순서대로 처리합니다. 작업 권한은 읽기, 자료 커밋, Pages 게시로 분리합니다. 자동 토큰이 만든 커밋의 후속 push 실행에 의존하지 않습니다. 진행 중 main에 새 소스 커밋이 생기면 오래된 실행은 저장을 중단하고 대기 중인 최신 실행이 재수집합니다. 강제 push는 하지 않습니다.

개별 수집 실패는 이전 자료와 오류 상태를 함께 게시합니다. 빌드나 자료 검증이 실패하면 현재 Pages 배포를 유지합니다. 전체 수집 실패는 Actions 실행 결과와 자료 시각을 확인한 뒤 다시 실행하세요.

로컬 수집이 디렉터리 교체 사이에 중단되어 `data/`가 없고 `data.backup/`이 남았다면 다음 수집에서 복원합니다. staging 폴더를 운영 데이터로 직접 사용하지 마세요. 원본 자료를 임의로 비우거나 가짜 시각·지표를 입력하지 마세요.

실제 배포 성공 시각은 Pages 배포가 성공한 뒤 기록하므로 다음 스냅샷에서 확인할 수 있습니다. 화면의 최신 자료 판단에는 수집 성공 시각을 사용합니다.
