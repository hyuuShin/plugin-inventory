# Plugin Inventory 설계

작성일: 2026-10-26 · 상태: 사용자 승인 완료 (2026-10-26, “네 진행해”)

## 1. 목적과 합의된 범위

AI에 연결하는 skill, plugin, MCP가 빠르게 바뀌므로 관심 도구의 최근 변경과 유지보수 활동을 살펴보고, 용도와 사용법을 정리하는 개인용 웹앱을 만든다. 설치 목록을 가져오는 앱이 아니다. 사용자가 관심 있는 도구를 직접 등록한다.

사용자와 확인한 조건:

- 관심 도구와 메모는 공개되어도 된다.
- 관리 계정은 `hyuuShin`이다. 해당 계정은 로컬 `gh`에 로그인되어 있다. 현재 기본 활성 계정은 다른 계정이므로 이 프로젝트의 원격 작업에서는 `hyuuShin` 자격 증명을 명시적으로 선택한다. 다른 프로젝트를 위한 기본 계정 설정을 임의로 바꾸지 않는다.
- 관심 목록은 GitHub Issue 입력 양식으로 관리한다.
- 수집 대상은 GitHub의 공개 정보로 한정한다. SNS 연동은 하지 않는다.
- 유료 AI API를 사용하지 않는다. 자동 번역·생성형 설명은 제공하지 않는다.
- GitHub Pages에 배포하고 GitHub Actions에서 수집·갱신한다. 별도 서버, DB, 인증 서비스는 운영하지 않는다.
- 사용자는 관심 목록, 도구 상세, 주간 발견, 등록 항목을 포함한 목업을 확인했고 변경할 부분이 없다고 답했다. 이 답은 화면 구성에 대한 확인이며, 이 문서의 최종 승인은 별도로 받는다.

초기 관심 목록은 비어 있다. 목업의 도구·버전·수치·순위는 예시이며 실제 등록 데이터로 가져오지 않는다.

## 2. 목표, 제외 항목, 실패로 보는 결과

### 목표

1. 관심 도구의 최근 릴리스와 개발 활동을 한 화면에서 구분한다.
2. Skill / MCP / Plugin 유형, 용도 분류, 한국어 사용법 메모와 공식 문서 링크를 관리한다.
3. GitHub에서 찾은 관련 도구를 매주 근거와 함께 소개한다.
4. 목록의 추가·수정·제외부터 정기 수집과 Pages 배포까지 GitHub 안에서 운영한다.
5. 수집 실패, 오래된 자료, 비교 이력 부족을 사용자가 알아볼 수 있게 한다.

### 이번 범위에서 제외

- 설치 상태 탐지, 설치 버전 비교, 도구 실행·설치·자동 업데이트.
- GitHub 이외의 마켓플레이스, 패키지 저장소, SNS 수집.
- 유료 서비스, LLM 호출, 로컬 모델을 실행하는 서버, 자동 한국어 번역.
- 다중 사용자별 비공개 목록, 웹앱 자체의 로그인, 브라우저에 PAT 입력.
- 설치 가능한 도구인지에 대한 완전한 자동 검증, AI 품질 점수, 전체 GitHub를 포괄하는 순위.

### 피해야 할 결과

- 릴리스가 없거나 커밋이 적다는 이유만으로 관리 중단이라고 단정한다.
- 저장소 전체의 변경을 개별 skill의 변경으로 표시한다.
- 수집 실패를 활동 없음 또는 별 증가 0으로 표시한다.
- 원문 설명을 AI가 작성한 한국어 해설처럼 보이게 한다.
- 키, 토큰, 외부 저장소의 실행 코드를 배포물에 포함한다.
- 주간 발견 후보를 사용자의 선택 없이 관심 목록에 추가한다.

## 3. 검토한 접근 방법과 선택

| 접근 | 장점 | 부담 및 제약 | 결정 |
|---|---|---|---|
| 저장소의 YAML 목록을 직접 편집 | 구조와 운영이 가장 단순하고 변경 이력이 명확함 | 도구를 추가할 때 파일을 편집해야 함 | 비교 후 미선택 |
| GitHub Issue 양식으로 등록하고 Actions로 동기화 | 입력 양식·수정 이력·GitHub 인증을 재사용하고 별도 백엔드가 필요 없음 | 추가·수정·제외는 GitHub 화면에서 수행하고 사이트 반영까지 갱신 시간이 필요함 | 사용자가 선택 |

선택한 구조는 공개 정적 웹앱 + Issue 원본 목록 + Actions 수집기 + Git에 저장하는 JSON 스냅샷이다.

## 4. 작성자가 제안한 구현 선택

사용자가 특정 기술 스택이나 수집 주기를 지정한 것은 아니다. 아래는 운영 부담과 의존성을 줄이기 위한 작성자의 선택이며, 최종 문서 승인 시 함께 검토할 내용이다.

- 웹은 HTML / CSS / JavaScript ES modules로 만든다. 정적 파일을 복사·검증하는 작은 빌드 스크립트를 사용하며 SPA 서버나 프레임워크 런타임은 두지 않는다.
- 수집·동기화·검증 스크립트는 Node.js 22 이상에서 실행한다. 내장 `fetch`, 파일 API, 테스트 실행기를 우선 사용한다. 실행 버전은 workflow에서 고정하고 지원 상태는 구현 시 재확인한다.
- 최초 원격 저장소명은 `hyuuShin/plugin-inventory`, Pages 경로는 `https://hyuuShin.github.io/plugin-inventory/`를 제안한다. 생성 전 기존 저장소 여부를 확인하고, 존재하면 내용을 확인해 덮어쓰지 않는다.
- 매일 09:17 KST에 관심 목록과 후보 스냅샷을 수집한다. 매주 월요일 09:43 KST에 주간 발견을 발행한다. 스케줄은 UTC cron으로 명시하며 수동 실행도 제공한다.
- 출시 시 완성된 실제 사용법 문구나 관심 목록을 임의로 채우지 않는다. 사용자가 등록한 메모와 GitHub 저장소 설명·README 링크를 사용한다.
- UI는 한국어, 날짜·시간은 `Asia/Seoul`, 수치에는 천 단위 구분을 사용한다.

## 5. 화면과 사용자 흐름

목업의 밝은 바탕, 표 중심 관심 목록, 데스크톱의 우측 상세 영역을 기준으로 한다. 색은 새 릴리스·활동 증거·주의 상태에 제한한다. 임의의 KPI 타일이나 장식 차트는 추가하지 않는다.

### 관심 목록

- 이름, 용도, 유형, 최근 릴리스, 유지보수 근거를 표시한다.
- 관심 도구 수, 최근 7일에 발행된 안정 릴리스 수에 해당하는 도구 수, 상태 확인이 필요한 도구 수를 표시하고 필터로 사용한다. 숫자는 현재 데이터로 계산한다.
- 이름·분류·메모 검색, 유형 필터, 용도 필터, 최근 활동/이름 정렬을 제공한다. 검색은 한글 조합 입력을 방해하지 않는다.
- 릴리스 발행일을 표시하는 `7일 내 새 릴리스`와 이전 수집 대비 새 릴리스 관측은 다른 개념이다. 주 표에서는 발행일 기준 표시를 쓰고, 상세에는 이전 스냅샷 대비 변경 여부를 쓴다. 설치 버전이 없으므로 `업데이트 필요`라고 표현하지 않는다.
- 전체 목록은 20개씩 더 보기로 탐색한다. 필터·정렬·선택한 도구를 URL에 저장하고, 필터 변경 시 표시 범위를 초기화한다.
- 처음 등록한 도구가 없으면 첫 등록 안내를 보여준다. 검색 결과 없음, 등록 오류, 일부 수집 실패는 각각 구분한다.

### 도구 상세

- 유형, 용도, GitHub 원문 설명, 사용자 메모, 공식 README/추적 경로, 릴리스와 변경 기록, 등록 Issue 링크를 제공한다.
- 최근 안정 릴리스와 최근 커밋을 분리한다. 경로 단위 도구는 저장소 릴리스임을 명시한다.
- 최근 12주의 커밋 활동은 해당 추적 범위의 자료로 만든다. API 집계 한도로 기간 전체를 읽지 못했다면 `집계 일부`를 표시하고 미확인 구간을 0으로 채우지 않는다.
- 메모가 없으면 `사용법 메모를 추가할 수 있습니다`와 Issue 수정 링크를 제공한다. 원문 설명이 없으면 설명 없음으로 표시한다.
- 모바일에서는 도구 선택 시 상세를 열고 목록으로 돌아갈 수 있게 한다. 돌아왔을 때 검색·필터·목록 위치를 유지한다.

### 이번 주 발견

- 주차, 발행 시각, 수집 범위, 후보별 저장소 설명과 근거를 표시한다.
- 비교 가능한 후보 중 주간 별 증가가 큰 도구를 최대 5개 소개한다. 아직 이력이 부족한 새 후보는 별도 `새로 찾은 후보`에 최대 5개 표시한다.
- 근거는 실제 수집한 별 수 변화, 변경 일자, 보관 상태 등이다. 문서 제공 여부는 실제 확인한 경우만 근거에 포함한다.
- 후보는 원문 저장소와 README로 연결되고, `등록 검토`는 주소를 채운 GitHub 등록 양식으로 이동한다.
- 데이터가 부족하면 후보가 적게 나오거나 없는 상태를 그대로 표시한다. 첫 주부터 근거 없는 급상승 순위를 만들지 않는다.

### 등록과 수정

- 사이트의 `관심 도구 추가`는 GitHub Issue 양식을 새 탭으로 연다. 사용자는 GitHub에 로그인한 상태로 제출한다. 웹앱의 계정 표시는 목록 소유자이며 로그인 세션을 뜻하지 않는다.
- 입력 필드: GitHub 주소(필수), 표시 이름(선택), 유형(필수), 용도 분류(필수), 사용법 메모(선택).
- 분류는 개발 / 브라우저 / 문서 / 디자인 / 데이터 / 업무 자동화 / 조사 / 기타를 기본으로 하고, 필요하면 설정 파일로 추가한다.
- 수정은 등록 Issue 본문 편집, 목록에서 제외는 Issue 닫기, 복원은 다시 열기로 한다. 웹앱에는 해당 Issue의 수정·닫기 방법으로 이어지는 링크를 제공한다.
- GitHub 입력 양식과 사이트 데이터는 수집 후 동기화된다. 사이트에서 즉시 저장되었다는 메시지는 보여주지 않고, 마지막 반영 시각과 Actions 실행 링크를 제공한다.
- Issue를 닫으면 현재 목록에서 제외되지만 공개 Git 기록까지 지워지는 것은 아니다.

## 6. 등록 원본과 식별 규칙

- 해당 저장소의 열린 Issue 중 지정한 `watchlist` 라벨과 양식 구조를 가진 기록을 읽는다. PR은 제외한다.
- MVP에서는 작성자가 `hyuuShin`인 기록만 반영한다. 외부인이 만든 Issue는 관심 목록에 들어오지 않는다. 라벨만으로 권한을 판단하지 않는다.
- owner가 작성한 Issue의 현재 본문이 원본이다. 사용자 입력은 명령이나 템플릿 코드로 실행하지 않는다.
- 정규화한 추적 대상은 `repo ID + scope path`로 식별한다. 같은 저장소의 서로 다른 경로는 각각 등록할 수 있다. 같은 대상을 중복 등록하면 가장 작은 열린 Issue 번호를 사용하고 나머지는 중복 오류로 표시한다. 원본 Issue는 자동 삭제하지 않는다.
- Issue 번호는 목록 항목의 안정적인 ID로 쓰고, 저장소 숫자 ID는 이름 변경을 추적하는 데 쓴다.
- 잘못된 주소·필드 누락·지원하지 않는 ref는 해당 등록 항목에 `등록 확인 필요`와 이유를 표시한다. 다른 정상 항목의 수집·배포를 막지 않는다.
- 자동 댓글은 초기 범위에 포함하지 않는다. 등록 오류는 사이트의 해당 기록 및 Actions 요약에서 확인한다.

### 지원하는 GitHub 주소

1. 공개 저장소 주소 `https://github.com/owner/repo`.
2. 기본 브랜치의 디렉터리 주소 `.../tree/<default-branch>/<path>`.
3. 기본 브랜치의 파일 주소 `.../blob/<default-branch>/<path>`.

기본 브랜치 이름은 GitHub API로 확인하고, 슬래시가 포함된 브랜치명도 전체 prefix로 해석한다. 파일 주소는 그 파일을 추적하며 상위 폴더로 임의 확장하지 않는다. 특정 tag/SHA, 기본 브랜치가 아닌 주소, GitHub 외 URL, URL 자격 증명과 임의 포트는 지원하지 않는다. 원본 대상은 등록 시 확인하고 URI fragment/query는 추적 식별에서 제거한다.

등록 경로의 최신 커밋과 활동은 `commits?path=...`로 수집한다. 경로가 삭제되면 삭제 커밋을 확인하고 경로 없음 상태를 표시한다. 임의로 저장소 전체 추적으로 바꾸지 않는다. 경로 이동을 사용자가 수정하면 추적 이력을 새 범위로 시작한다.

## 7. 데이터 모델과 보존

파일 구조의 구체적인 이름은 구현자가 다듬을 수 있으나 다음 책임은 분리한다.

| 자료 | 주요 내용 | 원본 및 보존 |
|---|---|---|
| 앱 설정 | 소유자, 저장소, 기본 경로, 분류, 수집 설정 | Git의 설정 파일 |
| 관심 등록 기록 | Issue 번호, 표시 이름, 유형, 분류, 메모, 정규화한 대상, 등록 검증 상태 | Issue에서 매번 재구성 |
| 도구별 최신 정보 | 저장소 ID/이름, 설명, 별 수, 보관 상태, 기본 브랜치, 릴리스, 범위별 커밋, 오류와 수집 시각 | 최신 JSON, 마지막 성공 자료 유지 |
| 일별 관측 | 날짜별 별 수, 릴리스 ID, 범위별 최신 커밋 SHA, 자료의 유효성 | 최근 90일, 마지막 1개 관측/일 |
| 주간 발견 | 주차, 선택된 후보, 원문 설명, 점수 근거, 비교 기간, 발행 시각 | 최근 52주 JSON |
| 실행 상태 | 시도 시각, 마지막 성공 시각, 부분 실패 여부, 실행 링크 | 최신 JSON |

배포용 자료에는 필요한 공개 필드만 포함한다. 전체 Issue 본문, 커밋 작성자 이메일, 토큰, API 응답 헤더, 실행 환경은 게시하지 않는다. 최근 데이터는 Git 커밋으로 영속화하므로 Actions 캐시나 임시 artifact의 보존 기간에 의존하지 않는다. 보존 기간이 지난 관측은 현재 파일에서 정리하지만 과거 Git 이력은 남는다.

처음 지원하는 규모는 최대 100개의 열린 등록 기록과 최대 200개의 발견 후보다. 초과 기록은 누락시키지 않고 상한 초과로 표시한다. 수집 요청·페이지 수에는 명시적인 예산을 두고 초과 시 불완전 자료임을 기록한다. 구체적인 예산과 요청 병렬도는 GitHub 제한에 맞춰 구현자가 정한다.

## 8. 업데이트와 유지보수 판정

- 릴리스는 발행된 안정 릴리스의 ID, tag, 발행일, 링크를 저장한다. 초안과 prerelease는 기본 표시에서 제외한다. Git tag와 GitHub Release는 같은 자료로 취급하지 않는다.
- 최신 릴리스가 없으면 저장소 조회 성공과 릴리스 목록 조회 성공을 확인한 뒤에만 `릴리스 없음`으로 표시한다. 404나 권한 오류를 자동으로 릴리스 없음으로 해석하지 않는다.
- 경로 단위 항목에서도 릴리스는 `저장소 릴리스`라는 범위를 함께 표시한다. 해당 skill 자체의 버전이라고 추론하지 않는다.
- 유지보수 근거는 범위별 최근 커밋 날짜, 최근 활동 집계, 저장소의 archived 상태다. `정상/중단` 같은 단일 종합 점수를 만들지 않는다.
- `상태 확인 필요`는 보관된 저장소, 삭제·접근 불가가 확인된 대상, 유효하지 않은 등록을 포함한다. 90일 이상 커밋이 없는 항목은 `최근 90일 변경 없음`으로 따로 표시하며, 관리 중단으로 분류하지 않는다.
- 최근 커밋이나 릴리스의 ID가 이전 성공 자료와 달라지면 `이전 확인 이후 변경` 근거를 남긴다. 첫 수집은 비교 기준 생성이며 신규 업데이트로 단정하지 않는다.
- 한 필드의 API 수집 실패는 그 필드의 마지막 성공 자료와 오류 상태를 함께 유지한다. 오래된 자료로 최근 7일 릴리스 수를 계산하면 마지막 성공 기준이라는 점을 표시한다.

## 9. GitHub 내 주간 후보 발견

GitHub Search API로 관련 저장소 후보를 수집한다. 비공식 Trending API나 HTML 스크래핑에는 의존하지 않는다.

초기 검색 묶음은 관련 topic과 이름·설명을 이용한다: `mcp-server`, `model-context-protocol`, `agent-skills`, `claude-code` plugin 관련 검색. 정확한 검색 문자열은 설정으로 관리하고 결과 적합성을 실제 응답으로 검증한다. 검색 결과는 설치 가능한 plugin의 확정 목록이 아니라 관련 후보로 표시한다.

- fork, archived, 기존 관심 대상과 같은 저장소의 후보는 소개에서 제외한다. 개별 경로가 등록된 저장소도 후보 중복 제외의 저장소 단위 기준에 포함한다.
- 주간 검색으로 새 후보를 보충하고 일별 수집으로 추적 후보의 별 수를 관측한다. 최초 실행에서는 후보 검색과 첫 관측을 수행하고, 주간 발행물이 없다면 비교 이력 없는 신규 후보만으로 첫 자료를 만든다. 발견 시각과 마지막 성공 시각을 보존한다.
- 주간 별 증가값은 실제 두 관측값의 차이다. 발행 시점과 가장 가까운 성공 관측, 그로부터 약 7일 전(6~8일 범위)의 성공 관측을 비교하고 실제 기간을 함께 표시한다. 범위 내 기준이 없으면 증가값은 미확인이다.
- 증가값이 양수이고 비교 기간이 유효한 후보를 증가 수, 최근 활동, 전체 별 수, 저장소명 순으로 정렬한다. 점수나 별 수를 생성하지 않는다.
- 비교 가능한 후보가 적으면 소개 수를 줄인다. 이력이 부족한 후보는 별도 신규 발견 목록으로 구분한다.
- 추적 후보 상한에서 기존의 유효한 주간 비교 대상은 해당 주의 발행까지 유지한다. 신규 후보는 남은 슬롯에 넣고, 주간 발행 후 오래되고 관심도가 낮은 후보부터 교체한다. 추적 범위와 제외 수는 실행 요약에 남긴다.
- 검색이 불완전하거나 실패한 주는 이를 표시한다. 전체 GitHub의 급상승 순위 또는 GitHub 공식 Trending이라고 부르지 않는다.

## 10. Actions 수집·저장·배포

기본 흐름은 `Issue 읽기 → 등록 검증 → GitHub 공개 자료 수집 → JSON 검증 → 변경 자료 커밋 → 정적 사이트 생성 → Pages artifact 배포`다.

- owner의 등록 Issue 생성·수정·닫기·재열기, 기본 브랜치 push, 일별/주별 schedule, `workflow_dispatch`를 처리한다. 수집 기준이 Issue의 현재 전체 상태이므로 일부 이벤트가 합쳐져도 최종 상태를 재구성할 수 있다.
- 읽기·수집 작업과 Git 변경·Pages 배포 작업의 권한을 구분한다. 수집은 필요한 읽기 권한만, 자료 커밋에는 contents 쓰기, 배포에는 pages 쓰기와 id-token 쓰기를 부여한다. 전체 workflow에 불필요한 쓰기 권한을 주지 않는다.
- Actions 자동 토큰으로 만든 데이터 커밋이 다음 push workflow를 실행할 것이라고 기대하지 않는다. 데이터 변경을 저장한 실행에서 검증·빌드·배포까지 직접 이어서 수행한다.
- 정기 수집·Issue 동기화·배포를 하나의 repository concurrency group으로 직렬화한다. 실행을 진행 도중 취소해 자료를 잃지 않게 하고, pending 실행이 합쳐질 경우 최신 전체 상태를 다시 읽는다.
- 게시 전 데이터 schema와 정적 파일 참조를 검증한다. 소스 코드 빌드 실패나 JSON 구조 오류면 현재 Pages 배포를 유지한다.
- 개별 대상의 API 실패는 마지막 성공 자료 및 오류 표시를 사용해 가능한 부분을 배포한다. 수집이 전부 실패해도 자료 구조가 유효하면 이전 자료와 실패 시각을 함께 게시할 수 있다. 실패 상태 게시마저 실패하면 마지막 게시 자료가 남으므로 사이트 자체의 경과 시간 표시가 필요하다.
- lastAttemptAt, lastSuccessfulAt, lastPublishedAt을 구분한다. 관심 자료가 48시간 이상 갱신되지 않았거나 주간 자료가 9일 이상 지났으면 오래된 자료 안내를 표시한다. 자동 실행은 정확한 시각을 보장하지 않는다.
- 수동 갱신 링크는 인증 없이 수집하는 버튼이 아니라 GitHub Actions 수동 실행 화면으로 이어진다.
- 공개 저장소의 예약 workflow는 60일간 저장소 활동이 없으면 꺼질 수 있다. 현재 실행 상태, Actions 링크, 다시 켜는 방법을 README에 남기며 시간 경과에 따른 오래된 자료 표시를 유지한다.

GitHub Actions 표준 Linux 실행기만 사용한다. 장기간 artifact/cache 보관이나 larger runner를 사용하지 않고 Pages artifact는 배포에 필요한 짧은 보존 기간으로 설정한다. 별도 유료 API 자격 증명은 요구하지 않는다. GitHub의 사용 한도와 정책 범위 안에서 동작하며 무조건적인 비용·가용성 보장은 하지 않는다.

## 11. 정적 웹의 동작과 경계

- 사이트는 빌드된 JSON만 읽는다. 방문할 때마다 GitHub API를 호출하지 않는다.
- 상대 URL과 설정된 base path를 사용하여 `/plugin-inventory/` 하위 경로에서 동작한다. 서버 rewrite가 필요 없는 query/hash 기반 화면 전환을 사용한다.
- 외부 문서·Issue·Actions 링크는 실제 대상과 새 탭 여부를 알 수 있게 제공한다. 저장소명은 배포 설정에서 가져오고 하드코딩하지 않는다.
- 외부 저장소 설명, 메모, Issue 제목은 텍스트로 출력한다. README나 릴리스 HTML을 그대로 삽입하지 않는다. 전체 문서는 GitHub로 연결하고, 사이트에는 필요한 짧은 원문 설명만 사용한다.
- 수집기는 검증한 GitHub API 경로만 요청한다. 임의 URL을 받아 대신 요청하거나, 원격 프로젝트를 checkout·실행·설치하지 않는다.
- 소스 저장소와 입력 자료를 실행 가능한 shell 문자열로 합치지 않는다. workflow event payload는 구조화된 JSON 파일로 읽는다.
- GitHub 토큰은 Actions와 계정을 명시한 로컬 관리 작업에서만 사용한다. 사이트, localStorage, URL, 로그에 토큰을 남기지 않는다.
- 반응형 표/목록, 실제 버튼·링크, 키보드 포커스, 검색 지우기, 오류 텍스트, 화면 이동 시 포커스 복구를 제공한다. 운영용 설명에 스크립트 구현 세부사항을 노출하지 않는다.

## 12. 완료 조건과 검증

### 핵심 흐름

1. `hyuuShin`이 공개 GitHub 저장소 주소를 Issue 양식으로 등록하면 수집 후 실제 자료가 목록에 나타난다.
2. 같은 Issue의 분류·메모를 수정하면 반영되고, 닫으면 제외되며 다시 열면 복원된다.
3. 외부인 작성 Issue와 중복 등록은 원치 않는 대상 추가나 정상 수집 중단을 일으키지 않는다.
4. 저장소/경로 단위 추적, 릴리스 없음, 보관됨, 경로 없음, API 실패와 복구를 구분한다.
5. 후보의 주간 변화는 저장된 관측으로 재계산 가능하고 첫 주에는 비교 자료 부족이 명확하다.
6. Pages 하위 경로에서 링크, 새로고침, 화면 전환이 동작하고 공개 사이트에 토큰이나 목업 데이터가 없다.
7. 실제 배포된 페이지와 Actions 실행 결과를 확인하고, 최초 데이터와 오래된 자료 표시가 실제 상태를 설명한다.

### 필요한 검증

- 수집기: URL 정규화, 기본 브랜치 경로 해석, Issue 권한·파싱·중복, 범위별 데이터, 릴리스 판정, 별 수 차이, 보존, 부분 오류에 대해 결정적인 테스트를 둔다.
- 운영: `GITHUB_TOKEN` 데이터 커밋 뒤 같은 실행에서 배포되는지, concurrency가 최신 상태를 유지하는지, API rate limit 이후 기존 자료를 잃지 않는지 확인한다.
- 웹: 검색·유형/용도 필터·정렬·더 보기·상세·목록 복귀·등록 링크와 빈/오류 상태를 브라우저에서 확인한다. 1440/768/390px, 키보드, 한글 조합 입력, 좁은 화면의 가로 넘침을 점검한다.
- 배포 전: JSON schema, 정적 빌드, 모든 내부 URL의 base path, 비밀정보 및 예시 자료 누출 여부를 확인한다.
- 배포 후: 실제 Pages 주소가 응답하고, 최신 JSON과 공개 화면의 수집 시각·등록 상태가 일치하는지 확인한다.

## 13. 구현자가 정할 세부사항

사용자의 목적이나 범위를 바꾸지 않는 파일명, 함수 분리, 테스트 fixture 구조, CSS 토큰의 미세 조정, API 페이지당 항목 수와 재시도 간격, 적정 병렬도는 구현자가 정한다. API의 현재 응답과 제한을 검증해 정하고, 불완전 자료의 상태 표시는 유지한다.

원격 저장소 생성·Pages 설정·실제 배포는 이 문서 승인 후 작성하는 구현 계획의 범위에 포함한다. 기존 같은 이름의 저장소나 계정 정책 등 확인되지 않은 외부 상태가 있으면 읽기 확인부터 수행한다.
